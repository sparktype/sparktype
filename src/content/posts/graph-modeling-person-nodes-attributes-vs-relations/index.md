지식 그래프에 "사람" 노드를 넣다 보면 금방 막히는 질문이 생깁니다. 이 사람이 어떤 팀에 속하는지, 무엇에 전문성이 있는지, 누구와 자주 협업하는지를 **속성(property)으로 쌓을지, 별도 노드와 관계(relationship)로 분리할지**입니다. 가상의 예시로 이 결정을 정리합니다.

## 현재 상태를 가정해보기

`Person` 노드에 이름과 한 줄 설명만 있고, 관계는 "노트에 언급됨(MENTIONED_IN)" 정도로만 연결되어 있다고 합시다. 이 상태에서는 "이 기술 전문가가 누구지?" 같은 질문에 그래프가 답을 못 합니다. 정보가 구조화되어 있지 않기 때문입니다.

## 세 가지 옵션

### Option A — 속성 확장

`Person` 노드에 `role`, `team`, `expertise` 같은 필드를 직접 속성으로 추가합니다.

- 장점: 구현이 쉽고 바로 적용 가능, 쿼리가 단순
- 단점: 배열 속성 검색에 제약이 있고, 팀·전문성 간 교차 분석이 어려움 (예: "같은 팀이면서 같은 기술 전문가인 사람들"을 찾기 힘듦)

### Option B — 하이브리드 (추천)

기본 정보(이름, 이메일, 역할)는 속성으로 두고, 팀·전문성·커뮤니케이션 이력은 전용 노드와 관계로 분리합니다.

```cypher
// 팀 소속
MERGE (t:Team {name: "플랫폼팀"})
MERGE (p)-[:MEMBER_OF {since: "2024-01", role_in_team: "리드"}]->(t)

// 전문성
MERGE (e:Expertise {name: "Kafka", domain: "데이터 플랫폼"})
MERGE (p)-[:EXPERT_IN {level: 4, years: 3}]->(e)

// 업무 담당
MATCH (proj:Project {name: "example-project"})
MERGE (p)-[:RESPONSIBLE_FOR {scope: "전체 아키텍처"}]->(proj)
```

이렇게 하면 "Kafka 전문가는 누구?" 같은 쿼리가 자연스럽게 가능해집니다.

```cypher
MATCH (p:Person)-[r:EXPERT_IN]->(e:Expertise {name: "Kafka"})
RETURN p.name, r.level ORDER BY r.level DESC
```

- 장점: 검색·집계가 강력하고, 점진적으로 확장 가능
- 단점: 초기 모델링 비용이 있고, 데이터를 어떻게 채울지(자동 추출 vs 수동 등록) 규칙이 필요

### Option C — 완전 이벤트 소싱

모든 상호작용(미팅, 이메일, 리뷰)을 `Interaction` 이벤트 노드로 모델링해서, 시간순 이력을 완벽하게 재현할 수 있게 합니다.

- 장점: 이력 타임라인 완벽 재현, 패턴 분석 가능
- 단점: 노트 구조화 부담이 크고, 자동 추출이 어려워 유지 비용이 높음

## 선택 기준

세 옵션을 가르는 기준은 결국 **"이 정보로 어떤 질문에 답하고 싶은가"**입니다.

- 단순히 "이 사람이 어떤 역할인지" 정도만 필요하다면 Option A로 충분합니다.
- "이 기술은 누구에게 물어봐야 하지?", "이 프로젝트 담당자가 누구지?" 같은 교차 질문이 자주 나온다면 Option B가 맞습니다.
- "이 이슈를 예전에 누구와 논의했었는데 정확히 언제, 무슨 내용이었지?"처럼 시계열 재구성이 핵심 요구사항이라면 Option C를 고려하되, 그만큼의 유지 비용을 감당할 수 있어야 합니다.

실무에서는 Option B가 무난한 절충점이 되는 경우가 많습니다. 전부를 이벤트로 남기기엔 비용이 크고, 속성만으로는 교차 분석이 막히기 때문입니다. 다만 시작할 때부터 전체 인물 데이터베이스를 다 채우려 하지 말고, 범위를 좁혀서(예: 실제로 자주 참조하는 소수의 인물·팀만) 먼저 채워보고 확장하는 게 안전합니다.

## 자동 추출의 한계

노트에서 이름과 설명 정도는 자동으로 추출할 수 있지만, "이 사람이 어떤 팀 소속인지", "무엇에 전문성이 있는지" 같은 구조화된 정보는 자동 추출이 어렵습니다. 결국 별도의 구조화된 입력(전용 노트 템플릿, 폼)을 통해 수동으로 채워야 하는 부분이 남습니다. 이 수동 작업의 범위를 얼마나 좁게 유지할 수 있는지가, 이 설계가 실제로 유지 가능한지를 가르는 기준이 됩니다.

## 개인정보 관점의 주의사항

인물의 소통 스타일이나 상호작용 이력 같은 정보는 민감할 수 있습니다. 로컬 환경에만 두고 쓴다면 괜찮지만, 클라우드에 동기화하거나 여러 사람이 접근하는 시스템으로 옮긴다면 접근 제어와 보관 정책을 먼저 정해야 합니다. 그래프 스키마를 설계하는 단계에서부터 "이 필드가 외부에 노출돼도 괜찮은가"를 함께 검토하는 게 좋습니다.
