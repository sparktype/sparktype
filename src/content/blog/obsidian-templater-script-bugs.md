Obsidian의 Templater 플러그인으로 노트 자동화 스크립트를 짜다 보면 자바스크립트 배열 조작이나 에러 처리에서 비슷한 실수가 반복됩니다. 실제 리뷰에서 발견한 패턴 몇 가지를 정리합니다.

## 버그 1 — `splice(-1, 0, line)` 위치 오류

배열 끝에 항목을 추가하려던 코드에서 `Array.prototype.splice`의 음수 인덱스를 잘못 이해한 경우입니다.

```js
// 잘못된 코드
toKeep.splice(-1, 0, line);  // "마지막 요소 앞"에 삽입됨

// 올바른 코드
toKeep.push(line);  // 맨 뒤에 추가
```

`splice(-1, 0, x)`는 "배열 끝에 추가"가 아니라 **"마지막 요소 바로 앞에 삽입"**을 의미합니다. 배열이 `[a, b, c]`일 때 `splice(-1, 0, x)`를 실행하면 `[a, b, x, c]`가 됩니다. 한 번은 티가 안 나지만, 이 로직이 반복 실행되는 자동화 스크립트(예: 미분류 항목을 인박스로 되돌리는 처리)라면 실행할 때마다 마지막 줄이 계속 뒤로 밀리면서 파일 내용이 서서히 뒤섞입니다.

끝에 추가하는 게 의도라면 `push()`가 명확하고, 특정 위치에 정말 삽입해야 한다면 인덱스를 `length`(끝) 또는 `0`(처음) 기준으로 명시적으로 계산하는 게 안전합니다.

## 버그 2 — fallback 없는 에러 처리로 데이터 소실

```js
// 대상 파일이 없으면 알림만 뜨고 입력값은 사라짐
if (targetFile) {
  // ... 태스크 추가
} else {
  new Notice(`❌ 파일을 찾을 수 없음: ${targetPath}`);
  // 입력한 내용이 그냥 사라짐!
}
```

사용자가 대화형 입력(퀵애드 스타일)으로 값을 입력했는데, 대상 파일을 못 찾으면 `Notice`(토스트 알림)만 띄우고 끝나는 패턴입니다. 문제는 알림이 몇 초 뒤 사라지고 나면 사용자가 입력한 내용을 복구할 방법이 없다는 점입니다.

이런 "선택한 대상이 없을 수도 있는" 분기에는 항상 fallback 저장소를 둬야 합니다.

```js
// 개선안 — 실패 시 fallback 위치에 저장
if (targetFile) {
  // ... 태스크 추가
} else {
  const inboxFile = app.vault.getAbstractFileByPath('Inbox.md');
  const content = await app.vault.read(inboxFile);
  const newContent = content.replace(/(## 미처리 항목\n)/, `$1${task}\n`);
  await app.vault.modify(inboxFile, newContent);
  new Notice(`⚠️ 대상 없음 → Inbox에 추가: ${taskName}`);
}
```

일반화하면: **사용자 입력을 받는 자동화 스크립트의 에러 경로는 "입력을 버리지 않는" 것을 최우선으로 설계해야 합니다.** 실패했다는 사실을 알리는 것보다, 실패했을 때 입력이 어디로 가는지가 더 중요합니다.

## 버그 3 — 쿼리 엔진이 인식 못 하는 데이터 형식

```
# Dataview의 TASK 쿼리에서 인식되지 않음 (체크박스 없음)
- 🔜 항목명 [repeat:: daily] [completion:: 2026-05-13]

# 올바른 형식
- [x] 항목명 [repeat:: daily] [completion:: 2026-05-13]
```

Dataview 같은 쿼리 플러그인은 마크다운의 체크박스 문법(`- [ ]` / `- [x]`)을 기준으로 태스크를 인식합니다. 이모지나 자유 텍스트로 상태를 표시하면 사람 눈에는 똑같아 보여도 쿼리 결과에서는 조용히 빠집니다. 대시보드에 "오늘 할 일"이 안 뜨는데 파일에는 분명히 적혀 있다면, 십중팔구 이 문제입니다.

## 버그 4 — 하드코딩된 섹션 vs 동적 쿼리

새 항목을 추가할 때마다 대시보드 파일을 수동으로 고쳐야 한다면, 애초에 설계가 잘못된 신호입니다.

| 현재 방식 | 대안 |
| --- | --- |
| 각 프로젝트별 고정 섹션 + 쿼리 반복 | `GROUP BY` 하나로 전체를 동적 나열 |

Dataview라면 이렇게 바꿀 수 있습니다.

```dataview
TASK
FROM "Projects"
WHERE !completed
GROUP BY file.name
```

## 정리

네 버그의 공통점은 "자동화 스크립트가 예외 상황을 과소평가했다"는 것입니다.

- 배열 조작은 의도(끝에 추가 vs 특정 위치 삽입)를 명시적인 메서드로 표현할 것
- 실패 분기는 항상 fallback 저장 경로를 가질 것
- 데이터 형식은 그걸 읽는 쿼리 엔진의 인식 규칙에 맞출 것
- 항목이 늘어날수록 수동 수정이 필요한 구조라면 동적 쿼리로 바꿀 것

노트 자동화든 다른 스크립트든, "이 코드가 반복 실행돼도 안전한가"와 "실패했을 때 사용자 입력이 사라지지 않는가"를 체크리스트로 삼으면 이런 종류의 버그를 미리 걸러낼 수 있습니다.
