## 한 줄 정의

**HTTP REST**는 HTTP/1.1 또는 HTTP/2 위에서 동작하는 리소스(URL) 중심 설계입니다. JSON 텍스트로 직렬화하고, 무상태(stateless)이며 캐시가 가능합니다. 브라우저와 모바일 어디서나 쓸 수 있습니다.

**gRPC**는 HTTP/2 위에서만 동작하는 함수(RPC) 중심 설계입니다. Protocol Buffers로 바이너리 직렬화하고, 양방향 스트리밍을 지원하며 `.proto` 스키마 정의가 필수입니다.

## 상세 비교

| 항목 | HTTP REST | gRPC |
| --- | --- | --- |
| 전송 프로토콜 | HTTP/1.1 또는 HTTP/2 | HTTP/2 전용 |
| 직렬화 | JSON (텍스트) | Protocol Buffers (바이너리) |
| 페이로드 크기 | 크다 (필드명 반복) | 작다 (필드 번호로 압축) |
| 파싱 속도 | 보통 | 빠름 (바이너리 직접 매핑) |
| 스트리밍 | SSE(단방향) / WebSocket | 단방향·서버·클라이언트·양방향 모두 |
| 코드 생성 | OpenAPI → 선택적 | protoc → 필수 (타입 안전) |
| 브라우저 지원 | 완벽 | gRPC-Web 필요 (프록시 필요) |
| 디버깅 | 쉬움 (curl, Postman) | 어려움 (grpcurl 필요) |

## 직렬화 비교: JSON vs Protobuf

같은 데이터를 표현할 때:

```json
{"id":1,"name":"Alice","age":30}
```

이 JSON은 39바이트인 반면, 같은 구조를 Protobuf로 표현하면 11바이트 정도입니다.

```protobuf
message User {
  int32 id = 1;
  string name = 2;
  int32 age = 3;
}
```

필드명 대신 필드 번호(1, 2, 3)를 1바이트로 인코딩하기 때문에 크기가 3~10배 절감됩니다. 숫자는 varint 인코딩, 문자열은 길이 접두사 방식이라 파싱 시 메모리 할당도 최소화됩니다.

## gRPC의 4가지 통신 패턴

| 패턴 | 설명 | 사용 예 |
| --- | --- | --- |
| Unary | 요청 1 → 응답 1 (REST와 동일) | 로그인, 단건 조회 |
| Server Streaming | 요청 1 → 응답 N개 스트림 | 실시간 로그 구독 |
| Client Streaming | 요청 N개 스트림 → 응답 1 | 파일 업로드, 센서 데이터 수집 |
| Bidirectional | 요청·응답 모두 스트림 | 채팅, 실시간 게임 |

## gRPC가 성능에 유리한 이유

1. **바이너리 직렬화** — JSON 문자열 파싱 대신 바이너리 직접 매핑. CPU 사용량과 페이로드 크기가 동시에 줄어듭니다.
2. **HTTP/2 멀티플렉싱** — 하나의 TCP 연결에서 수백 개의 RPC를 동시에 처리합니다. 연결 수립·TLS 핸드셰이크 오버헤드가 없습니다.
3. **헤더 압축(HPACK)** — 반복되는 HTTP 헤더를 색인으로 압축합니다. 소규모 메시지가 많을수록 효과가 커집니다.

서비스 간 통신(내부 MSA)에서 이 이점이 가장 극적으로 드러납니다. 초당 수만 건 이상의 RPC가 발생하는 환경에서 CPU·메모리·대역폭이 모두 절감됩니다.

## 그래도 REST가 유리한 경우

| 상황 | 이유 |
| --- | --- |
| 브라우저 ↔ 서버 직접 통신 | gRPC-Web은 프록시가 필요해 구조가 복잡해짐 |
| 퍼블릭 API (외부 노출) | REST가 범용성·문서화·캐싱에서 압도적 |
| 단순 CRUD, 낮은 트래픽 | gRPC 도입 비용(proto 관리, 빌드 파이프라인)이 이득보다 큼 |
| 캐싱이 중요한 경우 | HTTP GET은 CDN·브라우저 캐시 활용 가능, gRPC는 불가 |

## 실전 선택 기준

| 상황 | 추천 |
| --- | --- |
| 마이크로서비스 내부 통신 (고트래픽) | gRPC |
| 실시간 양방향 스트리밍 | gRPC |
| 다국어 서비스 간 타입 안전 통신 | gRPC |
| 퍼블릭 REST API | HTTP REST |
| 브라우저 → 서버 | HTTP REST |

현실에서는 **API Gateway(REST) + 내부 MSA(gRPC)** 혼합 구성이 가장 흔합니다. 외부에는 REST로 노출하고, 내부 서비스 간엔 gRPC를 써서 성능과 편의성을 동시에 잡는 방식입니다.
